# Notes

The bridge's decisions and their reasons. The entries up to 2026-10-15 were written in anywherellm-suite, when the bridge was one of its parts (`packages/bridge`), and keep the names of their day: the suite's `install --bridge`, `packages/shared`, `contract/`, `tools/check bridge`.

## The bridge, rewritten in TypeScript, 2026-10-15

- **From `anythingllm-toolkit` (Python), keeping its behaviour on the wire:** the routes, the allowlist's rules, the `{"error": ...}` shapes and statuses, the 120 s timeout, the key check's cache (60 s good, 10 s refused), the login that is read afresh and retried after a 401. The layers (`cli`, `api`, `adapters`, `core`) and their `Protocol` ports became nine flat files, because a function argument is enough to put a fake in at that size.
- **Renamed to `bridge` throughout.** The command is `anythingllm-bridge`, the file `bridge.env` in `~/.config/anythingllm-bridge/`, the port `BRIDGE_PORT`, `/health` says `"service": "anythingllm-bridge"`. `TOOLKIT_DATA` and `TOOLKIT_SERVICE` went with the venv and the service managers. **Two names are not changed yet and are the app's and the MCP servers' to follow:** the pairing link's `toolkit=` field (AnywhereLLM Lite reads it by that name), and what `packages/mcp` reads (`ANYTHINGLLM_TOOLKIT_URL`, `~/.config/anythingllm-toolkit/toolkit.env`, the `toolkit_client` package). The bridge writes `ANYTHINGLLM_BRIDGE_URL` into the servers' env files, so the MCP servers do not find it until they are moved in and renamed to match. Change them together. *(Done for the MCP side: see "The control server" below. The pairing link's `toolkit=` field is still the app's.)*
- **One file, no dependencies:** `node:http`, `fetch` and `util.parseArgs` replace FastAPI, httpx and Typer. The artifact is `dist/anythingllm-bridge.cjs`, with the default allowlist from `contract/default-allow.txt` inlined by esbuild. It is `.cjs` so that a fixed extension makes the file run the same wherever it is copied (`.mjs` would do as well; nothing needs CommonJS here, unlike the skills, which AnythingLLM `require`s). The target is Node 20, the system's.
- **Left out on purpose:** the launchd and Windows Task Scheduler managers (never run on real hardware), the venv building (there is no Python), `--container` discovery through podman or docker (`install --storage` only), `routes`, `logs`, the migration from earlier default allowlists (nothing is installed to migrate). `health` keeps the checks that still apply.
- **Tests import `src/` directly** (Node strips the types) and run the real server against a fake AnythingLLM on a port of its own, so one test covers login, key check, allowlist, forwarding and error shapes together. `bundle.test.mts` runs the built file. Not covered: a real `systemctl` (`service.test.mts` scripts it) and a real AnythingLLM.
- **One `package.json`, one `tsconfig.json` and one `build.mjs` for the JavaScript parts, at `packages/`.** `package.json` holds the toolchain (`typescript`, `esbuild`, `@types/node`), the scripts (`typecheck`, `bridge:test`, `skills:test`) and the `#shared/*` imports map; `shared:test` runs the helper's tests and `build.test.mts` (the boundary check), and `tools/check` runs it before either part's tests; there is one `node_modules/` and one lock, and the repository root gained nothing. There are no npm workspaces: nothing a part ships has a dependency. There is no `package.json` in `bridge/` or `skills/`; module types follow the extension (see above). The type-check covers both parts in one run, so `tools/check bridge` also type-checks the skills and the reverse, and the bridge is checked against Node 18's types (`@types/node` is pinned for the skills; the bridge targets Node 20 and uses nothing newer). `packages/mcp` is Python and not part of it. `tools/boundaries` lost its two ast-grep rules, which compared two Python packages. What remains of the rule "no part imports another": `build.mjs` fails a bundle that took in a file from outside its part (the bridge's `src/`, `shared/` and the contract; a skill's `src/` and `shared/`), the app is grepped, and a Python part cannot import a TypeScript one. A type-only import or one in a test is erased or not bundled, so the build check does not see it; a grep rule like the app's would.

## Follow-ups to the bridge, 2026-10-15

- **The boundary check has a test** (`packages/build.test.mts`): a bundle that takes in a file outside its allowed prefixes fails and leaves no output, `clean` is what is removed, and a prefix is a folder (`a/src-old/` is not `a/src/`). `build.mjs` exports `bundle()` and runs the builds only as the entry script.
- **A client that leaves ends the upstream call.** The server aborts a controller when the response closes unfinished, and `Upstream.exchange` passes the signal to `fetch` (with the timeout, through `AbortSignal.any`, Node 20.3+). The shared login and key check get no signal, since other callers wait on them. An aborted call is an `AbortError`, not a 502, and is not retried; it is logged as `client closed`. A POST may already have taken effect upstream, as with any dropped connection.
- **`service.usable` asks the manager, not the machine:** `systemctl --user is-system-running` answering running, degraded or starting, through the injected `Run`. That made the start path testable (`service.test.mts`) and changed one behaviour: a host with systemd but no user session bus (ssh without lingering) now gets the "run `serve` under your own supervisor" hint instead of a failing `enable`. `uninstall` and `health` key on the unit file existing, not on the manager answering: `uninstall` tries `disable --now` whenever `install` defined a unit and says so when systemctl refuses. The bridge needs Node 20.3 for `AbortSignal.any` (the README and `build.mjs` say so; nothing checks it at start).
- **Still not run:** a real `systemctl` and a real AnythingLLM.

## The bridge's service on each OS, and CI, 2026-10-15

- **`bridge/src/service/`: one interface, four managers.** `index.mts` has the interface (define, defined, start, stop, status, where the log is) and the choice: `BRIDGE_SERVICE` when set (`install --service`, saved; `auto` takes it out), else the OS's own manager when it answers, else foreground. Only the OS's own manager is asked. Uninstall and health look in the OS's own manager without asking whether it answers, so a unit defined earlier is found from an ssh session too. Ported from the Python toolkit's adapters, which never ran on real hardware either.
- **systemd** is the old `service.mts`, moved; its unit now follows `XDG_CONFIG_HOME`. **launchd**: an agent `local.anythingllm-bridge` in `~/Library/LaunchAgents`, loaded with `bootstrap`/`bootout` in `gui/<uid>` (which `launchctl print gui/<uid>` answering makes usable), `RunAtLoad`, kept alive after a crash only, its output in `~/Library/Logs/anythingllm-bridge.log`; the plist is written by hand (no plist library). **The Task Scheduler**: a logon task `anythingllm-bridge` running `%LOCALAPPDATA%\anythingllm-bridge\serve.cmd` (which sets `BRIDGE_ENV_FILE` and appends to `bridge.log`), running if its status says so or its last result is 267009 (SCHED_S_TASK_RUNNING, the same in every display language). New against the toolkit: it runs through `conhost.exe --headless`, so no console window stays on the desktop. That flag is undocumented (Windows 10 1809 and later have it); if it doesn't hold, a minimized window is the fallback. A task isn't restarted after a crash; the next logon starts it.
- **What tests them:** each manager's commands are scripted (`service.test.mts`), through install, uninstall and health, for all three OSes on any OS. Not run: launchd on a Mac, the Task Scheduler on Windows, and the real `systemctl --user enable` (it would put a unit into the developer's systemd).
- **`.github/workflows/test.yml`:** the type-check and every part's tests on ubuntu, macos and windows (Node 22), and `tools/e2e` on ubuntu. The tests that start a child now pass `SystemRoot` (Node on Windows needs it), and the install tests fix their platform to Linux, so their paths agree whatever runs them. The workflow hasn't run yet: it runs once the branch is pushed.
- **Not done from the plan:** a Node single-executable build (Node 20.3+ is the one thing to install), the zip in `tools/package` without Python, and a run on real macOS and Windows machines (install against AnythingLLM Desktop, the launchd agent after a logout, the hidden task window).

## Moved out of the suite, 2026-10-19

- **Why:** the suite is the control server and agent skills for AnythingLLM's own web GUI; only AnywhereLLM Lite needs the bridge. It moved here so neither repository carries the other's concerns (the control server came back here on 2026-10-20: see the last section). A fresh repository: the history up to the move is in anywherellm-suite (main `9c2fef6`).
- **Its own command,** `anywherellm-bridge` (`dist/anywherellm-bridge.cjs`): `install` points it at the storage, sets `BRIDGE_ALLOW` and starts the service; `uninstall` stops it and keeps the settings (the suite's uninstall used to forget the storage, which the suite's installer remembered in `bridge.env`); `health` checks the service, the bridge, AnythingLLM, the login, `BRIDGE_ALLOW` and the public route; `serve`, `pair` and `settings` are as they were. The settings file, the unit, the agent and the task keep their names, so the live instance moved by running `install` once.
- **The suite's helpers it used are copied in** (`upstream`, `envfile`, `paths`, `writeAtomic`, and `privateAddress`/`privateName` from the fence as `private.mts`), trimmed to what the bridge uses. The default list, `endpoints.md`, `versions.env`, `tools/e2e` (trimmed to the bridge) and `tools/routes` came with it.
- **Left as they were:** the launchd and Task Scheduler managers, the macOS and Windows CI, and the pairing link's `toolkit` and `apps` fields (`apps` names anythingllm-apps-v2, now archived).

## The fence's asks, 2026-10-20

*Superseded on 2026-10-21: the asks are gone (see the last section). Kept as the record of what was built and why.*

- **Why:** the suite's fence refuses every host on the owner's network unless `FENCE_ALLOW` names it, which kept the AnythingLLM assistant off a private ntfy server. Dropping the fence would open the LAN and tailnet to whatever a web page or an email tells the agent, and AnythingLLM's own `requestToolApproval` can't ask through the developer API (it denies without Telegram). So a skill asks the person in AnywhereLLM Lite during a chat it streams, and the bridge carries the answer.
- **Files, not a call:** the skills run inside AnythingLLM's container and can't reach the bridge (the fence refuses it, and `127.0.0.1` there isn't the host's). Both reach AnythingLLM's storage, so they share `<storage>/fence-lean/`: the skill writes `asks/<id>.json` and waits for its `decision`; the bridge writes it; `allowed.json` holds the addresses always allowed. The bridge locks a file as the suite's `updateJson` does (a `<file>.lock` folder, broken after 10 s), so either side may write.
- **An origin, not a host:** an always-allowed entry is one origin (scheme, host and port), so allowing SearXNG on `owen:8888` leaves AnythingLLM on 3001 and the bridge on 8467, on the same name, asking. A host-wide entry opened them too, background runs included. `FENCE_ALLOW` stays host-wide, as the person writes it. An origin holds `/`, so the route that forgets one takes it as `?origin=`, since the path is decoded once and an encoded `/` separates segments.
- **Only the phones' key decides:** the routes take the developer key named `AnywhereLLM` alone, looked up in AnythingLLM's key list and cached as the key check is; that one lookup is also what makes a key valid there, so `keyValid` isn't asked. Any other developer key, such as one the agent's MCP servers hold, is valid for the routes passed on; without the name check it could approve the agent's own ask.
- **What the bridge checks:** an id is 32 hex digits and a host a bare name or address, so no path leaves `fence-lean/`; an ask answered or past its `expires` is a 409, so a late tap never turns a refusal into a pass. The ask's text is the skill's, never the model's, and the bridge shows it as written.
- **`/health` says `asks`**, true only when `ANYTHINGLLM_STORAGE` is set, so a phone knows whether to look for asks without probing a path an older bridge would answer with a worded 403.

## The control server moved here from the suite, 2026-10-20

- **Why:** it and the bridge are the two users of AnythingLLM's internal API with its password (chat threads, scheduled jobs), and the bridge's default list already passed the same routes for the phone. Putting both here leaves the suite as the skills and the command that installs them, and the internal API in one repository. This reverses the 2026-10-19 reason above, "neither repository carries the other's concerns", for the agent's tools: the bridge now has a part the phone doesn't need, and a user with no phone can install only that (`install --control --no-start`).
- **Still a stdio server, not part of the service.** AnythingLLM starts `control.cjs` itself with its own `node` and environment (`AUTH_TOKEN`, `SERVER_PORT`), so the same file works for a container and for Desktop, and nothing depends on the bridge running. An MCP server on the bridge's HTTP port was set aside: the agent's tools would need the bridge up and a key in the servers file, and the servers file's `url` entries weren't checked for sending a header. It is a second esbuild entry (`src/control/main.mts`, target `node18`, the image's Node) whose text is inlined into the bridge's one file (`CONTROL_SOURCE`).
- **It uses the bridge's `Upstream`**, with the password read from `AUTH_TOKEN` in the environment, where it used its own client (that header already described the case). The `AbortSignal.any` the bridge's client uses when given a signal (Node 20.3) is never reached: the control server passes none. `target: node18` doesn't catch such a call, so `tools/e2e` is the proof: it starts `control.cjs` in the image, on its Node 18.
- **No MCP SDK.** The TypeScript SDK brings a dozen-plus transitive packages for what a stdio tool server uses: newline-delimited JSON-RPC and four methods (`initialize`, `ping`, `tools/list`, `tools/call`). `src/control/mcp.mts` is those, with a check of arguments against each tool's schema; it answers the client's protocol version when it knows it, else the newest. The cost is following the protocol by hand if a later version changes what a tool server must do.
- **Roles, not servers.** A role not asked for has no tools. Only `chat` is on by default, because a scheduled job runs a prompt as the agent, unattended: adding one plants an instruction that runs later. `schedule` is one tool with an `action` because AnythingLLM's MCP page (1.16) warns above 10 tools. `chat_clear` and `chat_delete` are shown first and read the chat back after, since AnythingLLM answers a delete with a bare `OK`.
- **`ControlError` is the one error to show the agent as it is:** the control server wraps whatever its client throws in it (the bridge's `BridgeError` included), and anything else is a bug, logged.
- **Install is polite to what it doesn't own** (`src/control/install.mts`). Other entries and the `anythingllm` block AnythingLLM keeps in ours stay; a `control` entry that isn't ours (decided by the path it starts, `anywherellm-bridge/control.cjs`) stops install; files are written in place, not renamed over, since a file in the storage may belong to its user and group *(since 2026-10-20 renamed over after all, keeping the mode: see the audit below)*; a storage the user can't write gets a message naming the fixes (the container's user, `podman unshare`, `--userns=keep-id`). The suite's earlier entry, which starts `anywherellm-suite/control.cjs`, is therefore not ours: the one live instance is moved by hand (its entry and file removed, then `install --control`), with no shim.
- **`default-allow.txt`'s chat routes** (`/workspace/*/threads` and the thread routes) were added for the control server's sake when it ran here before; the control server calls AnythingLLM directly, not through the bridge, so they stay only for the phone, which says whether it needs them.


## Links in the storage, and origins written another way: the audit, 2026-10-20

- **The storage is the container's to write, so the host follows no link in it.** `install --control` refused nothing: a link planted at `anywherellm-bridge/control.cjs` or the servers file, or a folder on the way that is one, made the host-side install write the link's target. Now a file, or a folder from the storage down to it, that is a link is refused (install, uninstall and health say which), and a file is written new (`wx`) and renamed over the old, so a link swapped in after the check is replaced, not followed. The rename keeps the old file's mode (`chmod`, whatever the umask: the live servers file is 664) and the folder's setgid keeps its group; the owner becomes whoever runs install, which was already the case for a file install made. A folder swapped for a link between the check and the write is still a race; the container would have to win it during an install.
- **An ask that is a link is a 403.** `readJson` opens with `O_NOFOLLOW`, so `GET /asks/<id>` and a decision never read another file of the host's into the phone's reply. Windows has no such flag and reads as before. The `asks/` folder itself isn't checked: a link there reaches only files named `<32 hex>.json`.
- **Origins compare as origins.** Always allow stores what `checkOrigin` returns (trimmed), and adding and forgetting compare each entry of `allowed.json` by its origin (`originOf`, the fence's rule), so an entry written another way (`HTTP://Host:80/`) isn't added twice and can be forgotten.
- **"Shown first" is enforced, not asked for.** `chat_clear`, `chat_delete` and the schedule's add, update and delete answered `apply: true` with no preview before it, so an agent told by a page or a message could delete any workspace's chat in one call. A preview now gives a `confirm` (16 random bytes, in the server's memory, the newest 100 kept), bound to the tool and its exact arguments but `apply` and `confirm`, good for 10 minutes and taken back by the first apply that names it, whether that apply then succeeds or not. A restart of the control server forgets them, so the agent previews again. It proves the change was shown by this server for exactly what is applied; whether the user agreed in between is still the agent's to ask, as the instructions say.

## The asks removed, and `GET /pages`, 2026-10-21

- **Why the asks went:** the user's rule is that the bridge, and each of the suite's skills, installs and works alone. An ask held a chat for up to two minutes waiting for an answer only AnywhereLLM Lite, through the bridge, could give, so a suite with no bridge had nobody to answer. The suite now refuses an address at once and the user lets one through on its own Vault page, under Allowed addresses; `allowed.json` is the suite's alone. So `asks.mts`, `/asks`, `/allowed`, the `asks` flag in `/health`, the lock half of `atomic.mts` (`updateJson` and its lock folders) and the 404, 409 and 503 errors went with them. No shim: the live `fence-lean/asks/` was empty, and is removed by hand.
- **`GET /pages`** gives Lite the paths of the suite's Library and Vault pages, which the agent no longer hands out once the suite's links switch is on (`anywherellm-suite pages --hide`). The suite's skills write them to `<storage>/anywherellm-suite/page-links.json`; the suite's `docs/page-links.md` is the contract, and now the only file the two repositories share. `/health` says `pages`, true when `ANYTHINGLLM_STORAGE` is set, as it said `asks`.
- **The same key rule as the asks:** only the developer key named `AnywhereLLM` (401 for a key not in the list, 403 for any other name). A path is a bearer capability (the page embeds the secret its events are checked with), so a key the agent's MCP servers hold must not learn it through the bridge.
- **A strict shape, because the container writes the file:** whatever runs in AnythingLLM's container (an agent skill, a tool) can write `page-links.json`. Answering what it holds would let it send Lite to any address, so a value is answered only when it matches `^/library-lean/[A-Za-z0-9_-]{24}\.html$` or `^/vault-lean/[A-Za-z0-9_-]{24}\.html$`, the two page tokens' form; anything else is `null`, not an error, and never echoed or logged. The paths are root-relative, so Lite joins them to the AnythingLLM address it already has.
- **The links file is read only as a plain file of at most 64 KiB:** besides a link (`O_NOFOLLOW`, as before), a pipe planted there would have held the bridge's one thread on `open` for ever, and a device or a huge file would have been read whole. It opens with `O_NONBLOCK` and checks the file with `fstat` before reading. Windows has neither flag.
- **Read at each call, not kept:** the file is a few hundred bytes, and a rotated token must show at once.

## The pairing link's QR code, 2026-10-22

- **`pair` draws the link as a QR code** when its output is a terminal, so a phone pairs from Lite's Scan QR code without a QR generator; piped, it prints the link alone, as before. The encoder is `qrcode-generator` (MIT, no dependencies), bundled, so the one file still needs nothing beside it. Each line is set in explicit white on black, so it scans on a dark theme too. Checked once by decoding a drawn code with zxing-cpp.

## The bridge on AnythingLLM's address, 2026-10-22

- **Why:** AnywhereLLM Lite learned the bridge's address only from a pairing link, and a connection saved by hand forgot it, so the phone lost Library, Vault and Upcoming with nothing to say why. Lite (c9ff180) now also asks `<AnythingLLM's address>/anywherellm-bridge/health`, on the same scheme, host and port only, and uses that prefix when it answers as the bridge.
- **The bridge strips the prefix itself** (`PREFIX` in `server.mts`), once, before any route is chosen: not every proxy strips it (a Cloudflare Tunnel path rule doesn't), and nothing further in needs a special case.
- **Install doesn't run `tailscale serve`:** that changes the machine's tailnet setup, needs sudo or the operator setting, and suits only one of the ways in. `health` checks the path instead (AnythingLLM's own page answering there is a fail) and names the command. `pair` and the :8467 address stay.
